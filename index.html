Régression linéaire et prévisions

Mesurer la relation entre deux variables, puis s'en servir pour prévoir. Deux jeux de données de TD, traités à la main puis vérifiés sous Excel.

Question

Est-ce qu'une variable en explique une autre, et peut-on prévoir la suite ? Je l'ai appliqué à deux cas d'entreprise :

  • Publicité et ventes : 8 mois de dépenses publicitaires et de ventes d'une boutique.
  • Chiffre d'affaires de la société Baudrum : ventes annuelles 2001–2004 et ventes par trimestre.

Méthode

  • Moyennes, écarts à la moyenne Xi, Yi
  • Droite des moindres carrés : a = ΣXiYi / ΣXi², b = ȳ − a·x̄
  • Coefficient de corrélation r et R²
  • Prévisions, puis répartition annuelle par trimestre
  • Vérification avec PENTE, ORDONNEE.ORIGINE, COEFFICIENT.CORRELATION

Tableau de calcul

  1. Publicité et ventes : relation très forte

    r ≈ 0,998. Chaque 1 k€ de publicité supplémentaire s'accompagne d'environ 3,10 k€ de ventes en plus. Pour 15 k€ de publicité, on prévoit environ 60,8 k€ de ventes.

  2. CA Baudrum : tendance nette à la hausse

    y = 9 400x + 67 000, r ≈ 0,93 (R² ≈ 0,86). Les ventes progressent en moyenne de 9 400 € par an, malgré le creux de 2002. Prévisions : 114 000 € en 2005 et 123 400 € en 2006.

  3. Une forte saisonnalité

    Le 3e trimestre pèse environ 36 % des ventes annuelles, le 4e seulement 16 %. La prévision de 2006 doit donc être répartie selon ce poids, pas en quatre parts égales.

  4. Les limites

    Une corrélation ne prouve pas la causalité. Avec 4 ou 8 points, la prévision reste fragile, et elle l'est encore plus quand on sort de la plage observée (par exemple 15 k€ de publicité alors que le maximum observé est 12 k€).

import numpy as np

pub    = np.array([2, 3, 5, 6, 8, 9, 11, 12])        # k€
ventes = np.array([20, 24, 30, 33, 40, 41, 48, 52])  # k€

X = pub - pub.mean()
Y = ventes - ventes.mean()

a = (X * Y).sum() / (X ** 2).sum()
b = ventes.mean() - a * pub.mean()
r = (X * Y).sum() / np.sqrt((X ** 2).sum() * (Y ** 2).sum())

print(f"y = {a:.3f}x + {b:.3f}   r = {r:.3f}")
print(f"Prévision pour 15 k€ : {a * 15 + b:.2f} k€")

# CA Baudrum : années numérotées 1 à 4
x  = np.array([1, 2, 3, 4])
ca = np.array([81000, 79000, 95000, 107000])

print("2005 :", a2 * 5 + b2, " 2006 :", a2 * 6 + b2)

Suivi micro-entreprise 2026

Un classeur pour qu'un micro-entrepreneur sache à tout moment ce qu'il a encaissé, ce qu'il doit à l'URSSAF et à quelle distance il est de son plafond.

Le besoin

Les micro-entrepreneurs paient leurs cotisations en pourcentage du chiffre d'affaires encaissé et doivent rester sous un plafond annuel. Beaucoup suivent ça « de tête », et découvrent trop tard qu'ils approchent du seuil.

Les 5 onglets du classeur

  • Mode d'emploi : comment remplir le fichier
  • Paramètres : type d'activité, année, table des taux
  • Recettes : journal des encaissements
  • Dépenses : journal des achats
  • Tableau de bord : cotisations par mois et par trimestre, revenu net, alertes et graphique

Déclarations trimestrielles

Taux et plafonds 2026 indicatifs (services : plafond de 83 600 €, vente : 203 100 €). Vérifiez votre taux exact sur urssaf.fr.

  1. Les paramètres sont séparés des calculs

    Quand l'URSSAF change un taux ou un plafond, on modifie une seule cellule dans l'onglet Paramètres, et tout le classeur suit.

  2. Une alerte avant le problème

    Le statut passe en « Attention » à 80 % du plafond, puis en « Dépassé ». L'utilisateur a le temps de s'organiser au lieu de le découvrir en fin d'année.

  3. Mensuel ou trimestriel

    Le tableau de bord calcule les deux, parce que le micro-entrepreneur choisit sa fréquence de déclaration.

  4. Pistes d'amélioration

    Gérer une activité mixte (vente + services avec deux taux), proratiser le plafond pour une création en cours d'année, ajouter le versement libératoire de l'impôt.

JavaScript : le calcul du simulateur de cette page
function tableauDeBord(mois, taux, plafond) {
  const ca = mois.reduce((s, m) => s + m, 0);
  const cotisations = ca * taux / 100;
  const part = ca / plafond;
  const statut = part >= 1 ? "Dépassé" : part >= 0.8 ? "Attention" : "OK";
  const trimestres = [0, 1, 2, 3].map(t =>
    mois.slice(t * 3, t * 3 + 3).reduce((s, m) => s + m, 0));
  return { ca, cotisations, net: ca - cotisations, part, statut, trimestres };
}

RESIL.IO est une application qui accompagne les femmes sous hormonothérapie après un cancer du sein hormonodépendant. J'ai analysé ses données pour décrire le suivi des traitements, la qualité de vie des utilisatrices, et le lien entre les deux.

Problématique

Comment les données de RESIL.IO permettent-elles de caractériser le suivi thérapeutique des utilisatrices et leur qualité de vie, et quelles analyses mettre en œuvre pour étudier la relation entre les deux ?

Données

  • treatment : 112 traitements renseignés
  • treatment_intake_log : 675 prises (taken / skipped)
  • daily_report : 495 rapports quotidiens
  • indicator_value et indicator : scores des 6 indicateurs

Démarche

  1. Explorer les tables et leurs identifiants
  2. Croiser les sources (jointures) et construire la population
  3. Décrire le suivi : nombre de prises, statuts, durée
  4. Décrire la qualité de vie, standardiser les 6 indicateurs
  5. Étudier les corrélations (Pearson et Spearman, seuil 5 %)

  • RStudio

5. Suivi et qualité de vie : corrélations

En vert : association significative (p < 0,05). En gris : non significative. Corrélations calculées sur les scores bruts.

  1. Construire la population avant d'analyser

    Sur 72 utilisatrices avec un traitement, 34 ont enregistré au moins une prise, et 30 ont aussi des données quotidiennes. Les résultats décrivent ces 30 utilisatrices, pas l'ensemble des utilisatrices de l'application.

  2. Des profils de suivi très hétérogènes

    De 1 à 247 prises et de 0 à 184 jours de suivi. 16 utilisatrices sur 30 ont 5 prises ou moins, et 13 ont un suivi de 5 jours ou moins. Les prises et la durée sont fortement liées (Pearson r = 0,920, p < 0,001).

  3. Sommeil et fatigue : les dimensions les moins favorables

    Après standardisation, l'humeur (7,30) et le brouillard mental (7,22) ont les meilleurs scores ; la fatigue (5,70) et la qualité du sommeil (5,51) les plus faibles.

  4. Pas de lien avec le nombre de prises

    Aucune corrélation significative entre le nombre de prises et les six indicateurs (toutes les p-valeurs > 0,5), ni avec le score moyen (r = 0,019, R² ≈ 0,0004).

  5. Deux associations avec la durée du suivi

    Plus le suivi est long, plus la fatigue tend à être faible (ρ = −0,400, p = 0,029) et le sommeil meilleur (ρ = 0,414, p = 0,023). Le brouillard mental suit la même tendance sans être significatif (p = 0,078).

  6. Association n'est pas causalité

    Avec 30 utilisatrices et des données d'observation, ces résultats sont exploratoires. On ne peut pas dire que suivre plus longtemps réduit la fatigue. Une prise non enregistrée n'est pas non plus une prise oubliée.

  7. Recommandations pour RESIL.IO

    Élargir la population, améliorer la régularité des saisies, passer à une analyse longitudinale individuelle et créer des indicateurs de qualité du renseignement des données.

R : standardisation et corrélations
library(readxl); library(dplyr); library(tidyr); library(ggplot2)

suivi  <- read_excel("suivi_30.xlsx")        # owner_id, nb_prises, duree_jours
scores <- read_excel("indicateurs_30.xlsx")  # owner_id, date, indicateur, valeur

# Moyenne de chaque indicateur par utilisatrice
moy <- scores %>%
  group_by(owner_id, indicateur) %>%
  summarise(score = mean(valeur, na.rm = TRUE), .groups = "drop")

# Standardisation : 10 = situation la plus favorable
negatifs <- c("Fatigue", "Bouffées de chaleur", "Douleurs articulaires")
moy <- moy %>% mutate(score_std = ifelse(indicateur %in% negatifs, 10 - score, score))

# Corrélations durée du suivi / chaque indicateur (Spearman)
base <- moy %>% select(owner_id, indicateur, score) %>%
  pivot_wider(names_from = indicateur, values_from = score) %>%
  left_join(suivi, by = "owner_id")

sapply(c(negatifs, "Qualité du sommeil", "Humeur générale", "Brouillard mental"),
       function(i) {
         t <- cor.test(base$duree_jours, base[[i]], method = "spearman", exact = FALSE)
         c(rho = unname(t$estimate), p = t$p.value)
       })

# Scores moyens standardisés
moy %>% group_by(indicateur) %>% summarise(m = mean(score_std)) %>%
  ggplot(aes(reorder(indicateur, m), m)) + geom_col(fill = "#0b7a5a") +
  coord_flip() + labs(x = NULL, y = "Score moyen standardisé (0-10)")

Le conflit de l'autoroute A69

Qui sont les acteurs du conflit autour de l'autoroute Castres–Toulouse, quel pouvoir ont-ils, et comment les rapports de force ont-ils changé ? Territoire étudié : le sud du Tarn et l'est toulousain.

Le livrable

  • Dossier écrit en six parties, bibliographie de 17 sources aux normes APA
  • Présentation de 38 diapositives, alignée point par point sur le dossier
  • Travail à six

La matrice CAPE

Elle classe les acteurs selon deux critères : sont-ils internes ou externes au territoire, et ont-ils un pouvoir de régulation ? On obtient quatre cases : Collectif, Arbitre, Privatif, Extérieur.

Mobilisation

Les opposants n'ont pas de pouvoir de décision. Ils compensent par l'opinion publique et le droit (recours).

  1. L'État n'est pas un arbitre neutre

    Il est placé en case Arbitre, mais il porte lui-même le projet. Les seuls arbitres indépendants sont les juges.

  2. Chaque case contient des partisans et des opposants

    Les élus, les agriculteurs ou les riverains sont divisés. Le conflit ne se résume pas à deux camps opposés case par case.

  3. Le conflit change d'échelle

    Avec le chantier en 2023–2024, les acteurs extérieurs (mouvements nationaux, médias, jusqu'à un rapporteur de l'ONU) font passer le conflit du niveau local au débat national.

  4. Deux coalitions

    D'un côté l'État, les élus locaux, ATOSCA, des acteurs économiques comme Pierre Fabre et une partie des habitants. De l'autre La Voie est libre, les associations environnementales, les Soulèvements de la Terre, le GNSA, des agriculteurs, des riverains et des scientifiques.

Traçabilité mobile money

Retrouver en quelques secondes une opération faite il y a 10 jours, même quand le SMS a été supprimé, et permettre aux détenteurs de cabines de suivre leurs transactions en temps réel.

Le problème sur le terrain

Un client revient à la cabine et dit : « J'ai fait une opération il y a 10 jours ». Pour la retrouver, l'agent n'a que deux sources :

  • Les SMS de confirmation, souvent déjà supprimés pour libérer la mémoire du téléphone
  • Le cahier où les opérations sont notées à la main, au jour le jour

Résultat : l'agent perd du temps à feuilleter le cahier, ne trouve parfois rien, et le client repart sans réponse. Le détenteur de la cabine, lui, ne voit pas ce qui se passe en temps réel.

La solution

  • Chaque opération est enregistrée au moment où elle est faite, avec une référence, la date et l'heure
  • Recherche instantanée par les derniers chiffres du numéro du client
  • Fonctionne sur un téléphone à touches, par un menu à code court (USSD)
  • Tableau de bord pour le détenteur de cabine : opérations de chaque agent, totaux du jour, en temps réel

Pour qui ?

  • Agents de cabine
  • Détenteurs de cabines
  • Clients

  1. Le vrai coût, c'est le temps de recherche

    Chaque réclamation oblige l'agent à fouiller le cahier pendant que d'autres clients attendent. Une recherche par numéro règle ce problème.

  2. Ne pas dépendre des SMS

    Les SMS restent sur le téléphone et disparaissent quand on les supprime. Un enregistrement centralisé garde une trace durable de chaque opération.

  3. Partir de l'outil de l'agent

    Les agents ont des téléphones à touches : le service doit marcher avec des menus numérotés, sans application à installer.

  4. Une valeur pour le détenteur de cabine

    Il suit en temps réel les opérations de chaque agent, compare avec sa caisse et repère vite un écart.

  5. Prochaines étapes

    Interroger des agents et des détenteurs pour valider le besoin, étudier l'accès à une passerelle USSD auprès d'un opérateur, sécuriser les données des clients, puis tester avec quelques cabines.

JavaScript : recherche d'une opération
// Retrouver toutes les opérations d'un client à partir des derniers chiffres
function rechercher(operations, chiffres, agent) {
  return operations
    .filter(op => op.client.endsWith(chiffres))
    .filter(op => !agent || op.agent === agent)
    .sort((a, b) => b.date - a.date);   // la plus récente en premier
}

// Totaux du jour pour le détenteur de cabine
function totauxDuJour(operations) {
  const auj = new Date().toDateString();
  const jour = operations.filter(op => op.date.toDateString() === auj);
  const somme = type => jour.filter(op => op.type === type)
                            .reduce((s, op) => s + op.montant, 0);
  return { nombre: jour.length, depots: somme("Dépôt"), retraits: somme("Retrait") };
}

      if (saisie === "*123#") aller("menu");
      break;
    case "menu":           // 1 Nouvelle op · 2 Rechercher · 3 Historique · 4 Total
      if (saisie === "1") aller("type");
      if (saisie === "2") aller("recherche");
      if (saisie === "3") afficherHistorique();
      if (saisie === "4") afficherTotal();
      break;
    case "recherche":
      afficher(rechercher(operations, saisie).slice(0, 3));
      break;
    case "type":    op.type = saisie === "1" ? "Dépôt" : "Retrait"; aller("montant"); break;
    case "montant": op.montant = Number(saisie); aller("client"); break;
    case "client":  op.client = saisie; aller("valider"); break;
    case "valider":
      if (saisie === "1") enregistrer({ ...op, ref: nouvelleRef(), date: new Date(), agent: "Agent A" });
      aller("menu");
  }
